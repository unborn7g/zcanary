ZCanary · privacy smoke test for Zcash apps

Your app says “private payment.” Did it really do that?

ZCanary checks the receipt, not the sign. It builds a throwaway Zcash network, makes your app pay with a secret marker attached, and inspects what actually happened.

  1. Start a practice network on your machine. No real money, seeds or keys.
  2. Pay through your app, with a secret marker in the payment.
  3. Inspect the real transaction, the receiving wallet and your app's logs.
  4. Report what passed, what failed, and what was never tested.

What the checks mean

C1 Network
Is everyone talking about the same network, or is the app quietly pointed somewhere else?
C2 Address
Does the address you pay offer a public (transparent) door as well as private ones?
C3 Public legs
Does the real transaction have any public inputs or outputs?
C4 / C4b Pools
Which shielded pools did the money use, and did value cross between them where the amount becomes visible?
MEMO Memo
Could the receiving wallet actually read the secret note we attached?
C6 Logs
Did our secret markers show up anywhere in the logs or files the app wrote?

A real find

While building ZCanary, the pool check caught something real. Zallet v0.1.0-beta.1 let a payment sent with the FullPrivacy setting move value from one shielded pool into another, which made the amount publicly visible. It reproduced on three separate test chains. The source and release notes suggest v0.1.0-beta.3 fixes it, but that was not run here.

What ZCanary does not test

A green report is a smoke test, not an audit. Every report ends with this list.

  • Network timing, IP/transport metadata, and observers outside the captured app outputs.
  • App databases, analytics, telemetry, crash dumps, or logs not explicitly configured for capture.
  • Mainnet/production behavior, real funds, and production credentials; this workflow is regtest-only.
  • Wallet/node combinations beyond those separately identified in docs/version-matrix.md.
  • Future transaction fields and pools are not decoded; detected unknown transaction fields make C3/C4/C4b fail closed, but those formats remain unverified.
  • C4b reports the transaction-derived fee and warns when it differs from conventional ZIP-317; it does not certify miner fee policy or infer hidden transparent input values.
  • NU7-era behavior and public testnet behavior, which are outside this phase's scope.
  • A complete privacy/security audit or a guarantee that no sensitive data can leak.
